# Phase 1.6: Dashboard - Design (short, rev. 2)

**Intent:** a Streamlit alerting dashboard for clients. It answers four questions:
1. Which companies are hiring unusually right now?
2. Which way is it moving?
3. Why does JobSignal think so?
4. Is the data current?

It reads **only** the read-only API (`/api/v1`). It never touches SQLite or the pipeline code.

**Brief:** "Deliver: predictive alerting dashboard" (Streamlit).
- Phase 1.4 user change: colour bands from the raw z (yellow at |z| = 3, red at |z| > 5).
- **Rev. 2 user changes (2026-11-01):**
  1. Resolve the cursor-pagination vs Streamlit mismatch.
  2. Every alert and company shows a Δ and a trendline, not a static z.

## Goals / non-goals / anti-goals
- **Goals:**
  - Banded, grouped, plain-English alerts, each with a **trajectory**: a sparkline of the
    cell's last 8 weeks, Δ vs baseline, Δ vs the previous week, and Δz vs the previous week.
  - Drill-down to the postings behind an alert.
  - A company view with **open-postings and new-postings trends**, composition, and postings
    on demand.
  - Freshness and health shown on the page.
  - A new pipeline run shows up within 60 s.
- **Non-goals:**
  - No logins.
  - No email or Slack delivery.
  - No pipeline triggers from the UI.
  - No forecasting model: "predictive" means early-warning signals with trajectories, not
    predicted future counts. That would be a later phase.
- **Anti-goals:**
  - The UI pulling every posting page-by-page to build a chart.
  - Showing stale data as current.
  - Rendering scraped text as HTML or markdown.
  - Leaking the API key.
  - Tracebacks shown to clients.
  - Unlabelled `mix_shift` caveats.
  - A trendline that disagrees with the stored score.

## 1. Pagination vs Streamlit: aggregate on the server, page rows on demand
**Measured on the local DB** (3 companies):
- Cursor-fetching every open posting takes 13 pages, 2,322 rows and 1.5 MB.
- That is **3.3 s cold / 0.67 s warm**, and it grows linearly with companies.
- One `/signals` call takes 0.07–0.13 s.

**Resolution:**
- **Charts and KPIs never need rows; they need counts. The server computes them in SQL.**
  - New `GET /api/v1/companies/{token}/composition` returns open postings counted by role
    family, seniority and country in one round trip.
  - New `GET /api/v1/company-trends` returns weekly open-postings and new-postings series for
    **all** companies in one round trip.
- **Rows are only for reading, so they load lazily:**
  - The postings table fetches **one page** (≤ 200, already filtered **on the server** by
    company, role family, seniority and country).
  - A **Load 200 more** button appends the next cursor page. Rows and the cursor live in
    `st.session_state`, keyed by the filter set; a filter change resets them.
  - In-table sorting works on the loaded rows, and the caption says so.
  - Nothing loops over cursors.
- **A guard test** counts HTTP requests per Companies-tab render and fails if it exceeds a
  fixed budget. That pins "no sequential prefetch" against regressions.
- **Rejected:**
  - A bulk-export endpoint: it moves the same 1.5 MB+ (growing) into every session for data
    the UI only summarises.
  - Pre-fetching in a background thread: Streamlit's script-run model makes this fragile, and
    it still ships every row.

## 2. Trajectory: computed on the server with the detector's own maths
**Fact:** a signal run stores only the **target week** per cell, so a trendline needs the
weekly history recomputed.

**Resolution:**
- **New `signals/trend.py`.** For one stored score, it recomputes the cell's last
  `TREND_WEEKS = 8` weeks:
  - each week's **value**: the opening count (volume) or the share of the company's openings
    (mix_shift);
  - each week's **z**, from the same `cell_counts` / `available_weeks` / `volume_scores` /
    `mix_shift_scores` functions, with the run's stored params.
- **Invariant (tested):** the last point's z equals the stored score's z. The trendline cannot
  disagree with the alert.
- **New `GET /api/v1/signals/trends?ids=…`** (1–50 ids) is batched. The Alerts table gets every
  sparkline in **one** call, and the events are loaded **once per company** involved, not once
  per id.
- **The dashboard derives the deltas** (pure, unit-tested):
  - **Δ vs baseline:** observed − baseline mean, or percentage points for mix_shift. No extra
    data is needed.
  - **Δ vs previous week:** the last value minus the previous available value.
  - **Δz vs previous week:** z(last) − z(previous).
  - The KPI tiles show the change in alert counts vs the **previous week's run** (the newest
    older run whose scored week differs).
- **Visuals:**
  - `st.column_config.LineChartColumn` sparklines in the Alerts and Companies tables.
  - Detail view: a value line with the baseline band (mean ± 3σ for volume), and a z line with
    the ±3 / ±5 rules.
  - Missing (uncovered) weeks are **gaps**, never zeros.
- **Honest cold start:** the volume detector needs at least 8 covered weeks, and scraping began
  in late October. Until that history exists, volume trends show mostly gaps labelled "not
  enough history". mix_shift trends work today, because published dates reach back.
- Caveat inherited from drill-down: trends use the current taxonomy, so they can differ
  slightly for runs scored under an older taxonomy version.

## Screens (one page, three tabs; filters in the sidebar)
| Tab | Shows |
|-----|-------|
| **Alerts** | KPI tiles with Δ vs the previous week's run. A z-score bar chart with bands. The alert-group table: band, company, cell, detector, direction, z, **Δz**, observed vs baseline, **Δ vs baseline**, **8-week sparkline**, provisional, "also at". Alert detail: plain-English explanation, trend chart, run params and drill-down postings |
| **Companies** | Company table: open postings, **Δ vs the previous week**, **open-postings sparkline**, **new-postings sparkline**, last scrape and its status, a stale flag. For one company: composition charts (server aggregates) and the lazy postings table (server filters + Load more) |
| **Runs & health** | API health and versions, the run history, the selected run's params |

## Decisions (assistant's calls - flag any to change)
- **Colour bands:** `red` when |z| > 5; `yellow` when 3 ≤ |z| ≤ 5; else `none`. Each band
  always carries a text label. The API's `severity` is shown unchanged.
- **Grouping overlapping levels:**
  - Group by company, detector, week and direction.
  - The headline is the max |z|. Ties go to the more specific level, then the lower id.
  - The rest are listed under "also at".
  - Sparklines come from the headline's cell.
- **API additions (Phase 1.5 extension):**
  - Three read-only `GET` routes under the same key, schema and opaque-error guards.
  - Their queries live in `storage/repository.py` and `signals/trend.py`.
  - Statement-count tests guard them against N+1 queries.
- **Layout:**
  - The logic lives in `src/jobsignal/dashboard/` (`client`, `alerts`, `trends`, `charts`,
    `app`, `serve`). `dashboard/app.py` is a 2-line entry point.
  - A test asserts that importing the dashboard never loads `sqlalchemy` or
    `jobsignal.storage`.
- **"Real-time":**
  - 60 s `st.cache_data` TTL, a **Refresh now** button, the run `as_of` and the last scrape
    time in the header.
  - A stale warning (last scrape > 36 h old, or not `ok`) names each affected company.
  - No polling timer (the data changes daily).
- **Security:**
  - Loopback-only binding (`.streamlit/config.toml` plus a launcher guard; remote binding needs
    `--allow-remote`, which warns there is no login).
  - Telemetry off and error details hidden.
  - Scraped text is rendered only via `st.dataframe`/`st.text`, with `http(s)`-only links. A
    test bans `unsafe_allow_html`.
  - The key is sent server-side only and never rendered.
- **New dependencies:** `streamlit` and `altair`.
- **Tests:**
  - Unit tests for the pure logic.
  - Client and app tests against the **real** API (FastAPI `TestClient` on a migrated tmp
    SQLite) via `streamlit.testing.v1.AppTest`.
  - Performance budgets checked in the live smoke.
