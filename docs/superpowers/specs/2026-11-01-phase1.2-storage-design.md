# Phase 1.2: Storage - Design (short)

**Intent:** persist every scrape so JobSignal can answer "how many postings did company X have
open (per department) at time T?" - the time series Phase 1.4's anomaly detection runs on - and
"when did posting P open and close?" - the raw material for Phase 2's posting-duration analysis.

**Inputs from Phase 1.1:** `Posting` objects (source, company, external_id, title, location_raw,
department, url, first_published, updated_at, fetched_at) produced per company per run.

## Goals
- SQLite now (`sqlite:///jobsignal.db`), PostgreSQL later with no schema rewrite.
- Every run and every per-company fetch is recorded, including failures.
- Exact history of which postings were open in each snapshot.
- Each posting has `first_seen_at` / `last_seen_at` / `closed_at` (Phase 2 duration).
- Scrape CLI persists by default; JSONL becomes an optional export.

**Non-goals:** harmonized roles/locations (1.3), anomaly queries (1.4), API (1.5), stock data
(Phase 2 adds its own tables keyed on `companies.id`), history of title/department edits.

**Anti-goal:** a failed or partial fetch must never look like a company closing its jobs -
that would fabricate exactly the "hiring freeze" signal clients pay to trust.

## Schema
| Table | Key columns | Constraints |
|---|---|---|
| `companies` | id, source, board_token, created_at | unique(source, board_token) |
| `scrape_runs` | id, started_at, finished_at, status | status in (running, succeeded, partial, failed) |
| `snapshots` | id, run_id→scrape_runs, company_id→companies, fetched_at, status, posting_count (NULL when failed), error_type | unique(run_id, company_id); status in (ok, partial, failed); index(company_id, fetched_at) |
| `postings` | id, company_id→companies, external_id, title, location_raw, department, url, first_published, updated_at, first_seen_at, last_seen_at, closed_at | unique(company_id, external_id); index(company_id, closed_at) |
| `snapshot_postings` | snapshot_id→snapshots, posting_id→postings | PK(snapshot_id, posting_id); index(posting_id) |

All timestamps go through a `UTCDateTime` column type: aware datetimes in, stored as UTC,
**aware UTC datetimes out**; naive datetimes are rejected on write.

## Lifecycle rules
- **Successful snapshot of company C at time T:**
  - Upsert each fetched posting on (company, external_id); new rows get `first_seen_at = T`.
  - Every fetched posting gets `last_seen_at = T` and `closed_at = NULL` (this also covers reopening).
  - Latest title/location/department/url/dates win.
  - Link every fetched posting to the snapshot.
  - Postings of C that are open (`closed_at IS NULL`) and **not** fetched get `closed_at = T`.
- **Incomplete fetch** (the source skipped malformed entries): `partial` snapshot - seen postings upserted and linked, **nothing closed**. *(added after final review)*
- **Stale snapshot** (older than the company's latest): rejected, recorded as `failed` with `error_type=StaleSnapshotError`. *(added after final review)*
- **Failed snapshot:** a row with status `failed` + `error_type`, `posting_count` NULL; postings untouched.
- **Run status:** `succeeded` if every snapshot is ok; `failed` if none is ok or partial; `partial` otherwise. A run is always finished (even on errors or Ctrl-C).
- **One writer at a time:** concurrent runs on the same database are not supported.
- Each company's snapshot commits on its own, so a crash later in the run keeps earlier companies.

## Approaches (history model)
1. **Membership table `snapshot_postings` + seen/closed columns (chosen, assistant's call).**
   - Gives exact open-set history per snapshot.
   - Counts at time T are a simple join.
   - Roughly 2.3k rows per run → about 840k rows per year at one run per day. Fine for SQLite.
2. Intervals only (`first_seen_at` / `last_seen_at` / `closed_at`, no membership).
   - Smaller.
   - Loses gaps: a posting closed and reopened looks like it was open the whole time.
   - Counts at T for past runs can be wrong.
3. Store raw JSONL per run and derive everything later. No queryable history; pushes the work into every consumer.

## Decisions (assistant's calls - flag any to change)
- **Duplicate tokens:** company tokens are deduplicated within a run (Phase 1.1 deferred minor; it would otherwise violate unique(run_id, company_id)).
- **CLI flags:**
  - `--db URL` overrides `JOBSIGNAL_DATABASE_URL`.
  - `--out` keeps writing JSONL only when given.
  - The CLI requires the schema to exist and exits 2 telling the user to run `alembic upgrade head`. It never auto-creates tables, so migrations stay the single source of schema truth.
- **Status columns:** plain strings + CHECK constraints (portable; no DB enum types).
- **Company metadata:** `companies.name` is omitted until a source supplies it (YAGNI).
